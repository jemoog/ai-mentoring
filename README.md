## 1. UCI 데이터 결합 (`src/uci_energy_integration.py`)

데이터: UCI Steel Industry Energy Consumption Dataset (2018년, 국내 철강공장, 15분 단위 35,040행, CC BY 4.0)
→ `uci_data/Steel_industry_data.csv`

| UCI에서 추출한 것 | 사용처 |
|---|---|
| **CO₂ 배출계수 0.4585 kgCO₂/kWh** (UCI CO₂ 컬럼 = 사용전력 × 계수를 10kg 단위 반올림, 재현율 99.87%) | 기존 Load_Type 임의 계수(0.35/0.45/0.60)를 대체 |
| **요일 × 15분 기저부하 프로파일** (평균 109.5kW, 평일 주간 226kW, 야간 20kW) | 라인 부하 + 공장 기저부하 = 공장 전체 수요전력 지표 |
| **요일 × 15분 UCI Load_Type** | 가상 TOU 요금 구분과의 정합성 확인 (평일 62.5% 일치) |
| 6주 확장 요금표 (`energy_context.csv`, `tou_tariff_extended.csv`) | 기존 1주 요금표 밖(9/28 이후) 공정 약 80개가 고정단가·피크 0으로 평가되던 편향 제거 |

참고: Load_Type별 CO₂/kWh 단순비율(Light 0.30, Maximum 0.45)이 달라 보이는 것은 저사용 구간의 반올림(0 처리) 효과이며, 최소제곱으로 보면 모든 Load_Type이 약 0.45로 같다. 즉 CO₂는 **어떤 공정이냐보다 얼마나 쓰느냐**로 결정된다.

## 2. 공통 평가 개선 (`src/metrics.py`)

- 6주 energy_context 기준 평가 (요금표 밖 공정 0개)
- CO₂ = kWh × UCI 배출계수 (기존 프록시 값도 `total_co2_kg_loadtype_proxy`로 함께 출력)
- 셋업 구간 = 가동전력 20% (스케줄러 내부 가정과 통일), 셋업·가공 경계 슬롯은 점유 비율로 분할 (중복 계산 제거)
- 신규 지표: 공장 전체 최대수요전력(UCI 기저부하 포함), 설비 대기전력 에너지, 최대 지연, 평균 단가
- `src/validate_schedule.py` : 공정 순서·설비 중복·가동시간·정비·셋업 정합성 검사

## 3. Slack-aware v2 (`src/slack_aware_energy_scheduler_v2.py`)

v1의 한계와 v2의 해결:

| v1 한계 | v2 해결 |
|---|---|
| slack을 현재 공정만 보고 계산 → 납기 위험 과소평가 | **하류공정 인지 slack** = 납기 − (최조 완료 + 후속 공정 가공시간) |
| 과부하 설비에서도 작업을 저요금대로 미룸 → 연쇄 지연 | **병목 보호**: 부하율 ≥ 0.8 설비는 이동 금지 (시나리오 실험으로 결정, 5장 참고) |
| Light/Medium 공정까지 이동 → 절감은 작고 지연만 증가 | **Maximum 공정만**, slack 24시간 이상일 때만 시간 이동, 이동 범위 = min(24h, slack × 50%) |
| EDD 순서 고정 | **작업 순서 local search** (swap/insert, 1500회, seed 고정) |
| 셋업을 '마지막 배정 제품' 기준 판단 → 셋업 누락 21~33건 | 시간상 직전/직후 공정 기준 판단 → **위반 0건**. 빈 구간에 끼워 넣을 때 직후 공정의 셋업을 빈 구간 안에 확보 |
| 공장 수요전력 미고려 | UCI 기저부하 + 라인부하가 650kW 초과 시 패널티 |

탐색 목적함수(납기 우선): `총지연(분) + 600 × 지연작업수 + 0.02 × 전력비용(원)`

# 4차시 – 부하율 시나리오 실험 + UCI 실측 주간 테스트

## 실행 방법

```bash
python src/scenario_generator.py                         # 시나리오 15개 생성 (약 40초)
python src/run_experiments.py --workers 2 --iterations 1000   # 전체 실험 (2코어 약 25분)
python src/uci_real_week_test.py --scenarios load070 load085 load100 load120 load148
```

결과: `experiments/` (`summary_by_load.csv`, `vs_edd_by_load.csv`, `vs_edd_by_scenario.csv`, `ablation.csv`, `uci_real_weeks_summary.csv`)

## 1. 실험 설계

- **부하율 5단계**: 병목 설비 부하율 70% / 85% / 100% / 120% / 148%(원본). 작업 수량만 조정해 목표 부하율을 맞춤 (`src/scenario_generator.py`)
- **데이터 3세트**: seed 0 = 원본 작업(투입·납기·제품) 유지 + 수량만 조정, seed 1·2 = 원본과 같은 분포로 새로 생성 → 총 15개 시나리오
- **비교 방식 6개**: FIFO, EDD, EDD_setup_correct(EDD 순서 + 셋업 누락 없는 배정 = 공정한 납기 기준선), Energy-aware v1, Slack-aware v1, Slack-aware v2 (순서탐색 1000회)
- **평가**: UCI 결합 공통 지표 + 제약 검증. 모든 수치는 seed 3개 평균

## 2. 실험 중 발견·수정한 v2 문제

1. **빈 구간 낭비 버그**: 빈 구간에 작업을 끼워 넣을 때, 직후 공정이 다른 제품인데 셋업 없이 배정돼 있으면 무조건 포기했다. 부하 85%에서 설비가 수 시간씩 비어 납기가 EDD보다 크게 나빴다(납기 내 50 vs 70건). → 직후 공정의 셋업을 빈 구간 안에 넣도록 수정 (셋업은 부품 도착 전에 하는 설비 준비로 간주, 검증기도 '가공 시작' 기준으로 공정 순서를 검사).
2. **연쇄 지연**: 부하율 85~100% 설비에서 고에너지 공정을 저요금대로 옮기면, 그 작업은 slack이 있어도 같은 설비를 기다리는 다른 작업들이 늦어졌다. 병목 기준을 1.0 → **0.8**, 이동 최소 slack을 8 → **24시간**으로 조정 (그리드 탐색 결과 납기 손실이 가장 작고 절감은 유지되는 조합).

| 85% | Energy-aware v1 | −32.5%p | +21,015분 | −5.5% | −31.1% | +1.9% |

| 148% | **Slack-aware v2** | **+7.9%p** | **−34,903분 (−16%)** | −1.6% | −6.9% | −0.1% |

- v2는 **15개 시나리오 전부에서 EDD보다 전력비가 낮았고**, 모든 부하율에서 납기 준수율이 가장 높았다.
  총 지연은 15개 중 13개에서 같거나 적었다 (나머지 2개는 지연 작업 수를 7~9건 줄이는 대신 총 지연이 585~1,075분 늘어남).
- **부하율이 낮을수록 에너지 절감이 크다**: 피크 시간대 에너지 −38%(70%) → −7%(148%). 설비에 여유가 있어야 고에너지 공정을 저요금대로 옮길 수 있다.
- **부하율이 높을수록 납기 개선이 크다**: 순서 탐색으로 셋업을 18~26% 줄여 병목 시간을 확보하기 때문.
- Energy-aware v1은 절감은 가장 크지만 납기가 심하게 무너진다(70%에서도 준수율 −26%p). v2는 그 절감의 약 2/3를 납기 손실 없이 얻는다.
- 원본 EDD는 셋업 누락(시나리오별 16~31건)으로 시간을 '공짜로' 얻고 있다. 셋업을 제대로 넣은 EDD(EDD_setup_correct)는 부하 85%에서 납기 준수율이 EDD보다 10%p 낮다. 즉 실제 v2의 개선 폭은 위 표보다 크다.

## 5. UCI 실측 주간 테스트

기본 평가는 UCI 1년치를 요일×시간 **평균**으로 쓴다. 평균은 실제 급등을 지우므로, 2018년 **실제 연속 주간 53개**를 그대로 기저부하로 넣어 공장 최대수요를 다시 계산했다 (`src/uci_real_week_test.py`, 53주 × seed 3 = 159회).

| 부하율 | v2: 피크요금 시간대 공장 최대수요 (EDD 대비) | EDD보다 낮은 비율 | v2: 하루 전체 최대수요 |
|---|---|---|---|
| 70% | **−14.1% (−120kW)** | 95% | +0.3% |
| 85% | −5.1% (−45kW) | 74% | +1.0% |
| 100% | −2.9% | 60% | +0.6% |
| 120% | −4.1% | 69% | −0.1% |
| 148% | +0.9% | 43% | +0.8% |

- 실측 변동을 넣어도 v2는 **피크요금 시간대의 공장 최대수요를 확실히 낮춘다** (부하 70%에서 159회 중 95%).
- 하루 전체 최대수요는 변하지 않는다(±1%). UCI 공장의 기저부하(최대 약 630kW)가 우리 라인(최대 429kW)보다 커서, 최대수요는 기저부하 급등 시점이 결정한다. 기본요금(최대수요 기준) 절감을 노리려면 기저부하 예측과 연동한 수요 상한 제어가 필요하다 → 향후 과제.

## 6. 결론

- **v2는 납기를 지키면서 에너지를 줄이는 방식**이다. 모든 부하율에서 EDD보다 납기가 좋고 전력비가 낮다.
- 에너지 절감 크기는 **설비 여유(부하율)**가 결정한다: 부하 70~85%에서 전력비 −4~8%, 피크 시간대 에너지 −22~38%.
- CO₂는 시간 이동으로는 줄지 않는다(±1%). 셋업·대기전력 같은 사용량 자체를 줄여야 한다.

## 한계
- 가상 생산 데이터 기반이다. 실제 공장 작업지시·설비 데이터로 검증이 필요하다.
- local search는 휴리스틱이라 최적해를 보장하지 않는다.
- 요금 구분(경부하/중간/최대)은 가상 TOU이며, UCI 공장의 실제 부하 구분과 평일 62.5% 일치한다.
- `src/tune_v2.py`는 배정 정책 파라미터 그리드 탐색 도구다 (원본 데이터 기준).
