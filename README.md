## 1. UCI 데이터 결합 (`src/uci_energy_integration.py`)

데이터: UCI Steel Industry Energy Consumption Dataset (2018년, 국내 철강공장, 15분 단위 35,040행, CC BY 4.0)
→ `uci_data/Steel_industry_data.csv`

| UCI에서 추출한 것 | 사용처 |
|---|---|
| **CO₂ 배출계수 0.4585 kgCO₂/kWh** (UCI CO₂ 컬럼 = 사용전력 × 계수를 10kg 단위 반올림, 재현율 99.87%) | 기존 Load_Type 임의 계수(0.35/0.45/0.60)를 대체 |
| **요일 × 15분 기저부하 프로파일** (평균 109.5kW, 평일 주간 226kW, 야간 20kW) | 라인 부하 + 공장 기저부하 = 공장 전체 수요전력 지표 |
| **요일 × 15분 UCI Load_Type** | 가상 TOU 요금 구분과의 정합성 확인 (평일 62.5% 일치) |
| 6주 확장 요금표 (`energy_context.csv`, `tou_tariff_extended.csv`) | 기존 1주 요금표 밖(9/28 이후) 공정 약 80개가 고정단가·피크 0으로 평가되던 편향 제거 |

참고: Load_Type별 CO₂/kWh 단순비율(Light 0.30, Maximum 0.45)이 달라 보이는 것은 저사용 구간의 반올림(0 처리) 효과이며, 최소제곱으로 보면 모든 Load_Type이 약 0.45로 같다. 즉 CO₂는 **어떤 공정이냐보다 얼마나 쓰느냐**로 결정된다.

## 2. 공통 평가 개선 (`src/metrics.py`)

- 6주 energy_context 기준 평가 (요금표 밖 공정 0개)
- CO₂ = kWh × UCI 배출계수 (기존 프록시 값도 `total_co2_kg_loadtype_proxy`로 함께 출력)
- 셋업 구간 = 가동전력 20% (스케줄러 내부 가정과 통일), 셋업·가공 경계 슬롯은 점유 비율로 분할 (중복 계산 제거)
- 신규 지표: 공장 전체 최대수요전력(UCI 기저부하 포함), 설비 대기전력 에너지, 최대 지연, 평균 단가
- `src/validate_schedule.py` : 공정 순서·설비 중복·가동시간·정비·셋업 정합성 검사

## 3. Slack-aware v2 (`src/slack_aware_energy_scheduler_v2.py`)

v1의 한계와 v2의 해결:

| v1 한계 | v2 해결 |
|---|---|
| slack을 현재 공정만 보고 계산 → 납기 위험 과소평가 | **하류공정 인지 slack** = 납기 − (최조 완료 + 후속 공정 가공시간) |
| 과부하 설비에서도 작업을 저요금대로 미룸 → 연쇄 지연 | **병목 보호**: 부하율 ≥ 1.0 설비는 이동 금지 |
| Light/Medium 공정까지 이동 → 절감은 작고 지연만 증가 | **Maximum 공정만** 시간 이동, 이동 범위 = min(24h, slack × 50%) |
| EDD 순서 고정 | **작업 순서 local search** (swap/insert, 1500회, seed 고정) |
| 셋업을 '마지막 배정 제품' 기준 판단 → 셋업 누락 21~33건 | 시간상 직전/직후 공정 기준 판단 → **위반 0건** |
| 공장 수요전력 미고려 | UCI 기저부하 + 라인부하가 650kW 초과 시 패널티 |

탐색 목적함수(납기 우선): `총지연(분) + 600 × 지연작업수 + 0.02 × 전력비용(원)`

## 4. 결과 (UCI 결합 공통 평가 기준)

| 지표 | FIFO | EDD | Energy-aware v1 | Slack-aware v1 | **Slack-aware v2** |
|---|---|---|---|---|---|
| 납기 내 작업 | 29 | 24 | 17 | 18 | **31** |
| 납기 준수율 | 36.3% | 30.0% | 21.3% | 22.5% | **38.8%** |
| 총 지연시간(분) | 240,735 | 185,880 | 209,875 | 192,865 | **153,490** |
| 총 셋업시간(분) | 2,310 | 2,220 | 2,220 | 2,220 | **1,345** |
| 전력비용(원) | 9,988,421 | 10,043,933 | 9,775,925 | 9,922,738 | **9,675,980** |
| 피크 겹침 슬롯 | 877 | 920 | **791** | 845 | 802 |
| 피크 시간대 에너지(kWh) | 17,751 | 18,958 | 16,539 | 17,358 | **16,375** |
| 공장 최대수요(kW) | **724.4** | 742.0 | 742.0 | 742.0 | 736.4 |
| CO₂(대기전력 포함, kg) | **33,070** | 33,225 | 33,301 | 33,179 | 33,118 |
| 제약 위반(셋업 누락) | 21 | 23 | 26 | 33 | **0** |

EDD 대비 v2: 납기 준수율 **+8.75%p**, 총 지연 **−17.4%**, 전력비 **−3.7%**, 피크 슬롯 **−12.8%**, 피크 에너지 **−13.6%**, 셋업 **−39.4%**

### 해석
- v2는 **납기와 에너지를 동시에 개선한 유일한 방식**이다. v1 계열은 에너지를 줄이는 대신 납기가 악화되는 trade-off였다.
- v2 개선의 대부분은 작업 순서 탐색이 같은 제품을 묶어 **셋업을 39% 줄이고**, 그만큼 병목 설비 시간을 확보한 데서 나온다. 실제로 시간 이동된 공정은 5개뿐이다.
- 그래서 피크 감소는 Energy-aware v1(−14.0%)과 비슷한 수준(−12.8%)이지만, 납기 손실이 없다.
- CO₂는 kWh에 비례(단일 배출계수)하므로 시간 이동으로는 거의 줄지 않는다(−0.3%). CO₂를 줄이려면 사용량 자체(셋업·대기전력)를 줄여야 한다.

### 한계
- 가상 데이터의 설비 부하율이 M01 128%, M02 148%, M03 147%로 1주 용량을 크게 초과한다. 어떤 알고리즘도 대부분의 납기를 맞출 수 없으며, 에너지 이동 여지도 작다(병목 설비는 이동 금지).
- 부하율을 70~85%로 낮춘 시나리오에서 v2의 에너지 절감 효과가 훨씬 크게 나타날 것으로 예상된다 → 다음 과제.
- local search는 휴리스틱이라 최적해를 보장하지 않는다 (seed 42/7/123에서 총지연 153~157천 분으로 안정적).
- `src/tune_v2.py`는 배정 정책 파라미터 그리드 탐색 도구다. 탐색 반복 수가 적으면(400회) 기본값보다 나쁜 결과가 나올 수 있어, 현재 기본값을 유지했다.
